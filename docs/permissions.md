# Permissions and recovery

gob.lin reads microphone, Accessibility and Input Monitoring status at launch, every second, on activation, and after wake. Launch can open onboarding, but never calls a permission-request API. Allow buttons are the only requests. Microphone status distinguishes not requested, denied, restricted, and allowed; after a decision its button opens Settings. Other rows show what their current macOS API reports, independently of shortcut availability.

Use `scripts/build.sh debug` and `scripts/launch.sh` for signed SwiftPM dogfood. The launcher verifies the exact bundle, rejects unsigned/ad-hoc or hash-bound validation signatures, prints its absolute bundle/executable paths and designated requirement, and refuses to start while another `GoblinApp` is running. It uses an explicit bundle URL and a new instance, avoiding activation of a different worktree. Quit the old process before rebuilding or switching bundles. For Xcode, build the signed Goblin target and pass the product's exact path to `scripts/launch.sh`; `--check` validates either configuration without launching. The local signing certificate is reused, not replaced. Xcode Debug uses a normal executable (`ENABLE_DEBUG_DYLIB=NO`): the generated debug-dylib layout fails hardened-runtime library validation with this local certificate. Hardened runtime and library validation remain enabled; Debug retains its existing debugger entitlement. SwiftUI's debug-dylib-dependent preview support is unavailable in this configuration.

When a toggle appears enabled but the app disagrees:

1. Open Permissions & onboarding and identify **which individual permission** is unavailable. Expand **Running app** and compare its bundle with the entry in System Settings. An old app with the same display name can have a different signing identity.
2. Return from Settings or choose **Check again**. Both refresh statuses and retry a failed shortcut even if no status changed. The retry calls the normal start path, so its existing permission gates remain enforced; a working tap is not restarted.
3. If the mismatch persists, quit gob.lin and reopen the same signed bundle. Some macOS permission changes require a new process. Recheck the row before changing the grant.
4. Collect local development diagnostics with the API statuses, actual bundle path, signing identifier/designated requirement, and tap-start result. Establish whether Settings registered a different build before manually removing/re-adding any entry. Do not routinely reset TCC or replace certificates.

Apple documents that [mutually compatible designated requirements share access to privacy-protected resources](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements). The same app name or bundle identifier alone does not establish that compatibility. A matching requirement is signing evidence, not proof of a particular hardware or TCC result.

A tap creation failure is reported as **Shortcut unavailable**, preserving the actual permission statuses. An allowed Accessibility API result does not prove that a stale grant caused the tap failure. A run-loop source failure is separately identified as local tap setup failure and recommends reopening/collecting diagnostics. No reset command is offered or executed. Successful tap startup clears the failure. Permission revocation invokes `onRevocation` before `onChange`, stops services safely, and clears its recovery notice when that permission is granted again.

Integration hooks:

- `PermissionModel.onRetry` is owned by `HotkeyService` and calls its idempotent `start()`. Preserve this when the required permission policy changes.
- `PermissionModel.Snapshot.diagnosticFields` exposes separate microphone/Accessibility/Input Monitoring API statuses. `PermissionModel.launchIdentity` provides local-only bundle/executable paths, version/build, PID, signing identifier, code hash, and designated requirement. The hash identifies a build; it is not the stable signing identity.
- Local unified-log events use subsystem `app.goblin.dictation.permissions`, category `recovery`: `launch_identity`, `permission_initial`, `permission_changed` (previous/status), and `tap_start` (`started`, `blocked_by_permissions`, `creationFailed`, or `runLoopSourceFailed`). The persistent development logger can consume the same metadata at `logDiagnostic`; this branch does not add a logging backend. Paths/signing details are not added to copied/shareable diagnostics.
- `HotkeyEventTap` delivers `Result<Void, StartFailure>` to distinguish creation from run-loop setup. Keep cancellation generation checks so obsolete tap results do not update a replacement service.

Run `scripts/check-permissions.sh` for focused synthetic status/retry/revocation probes and `scripts/check-launch.sh` after a signed build for launcher rejection checks on temporary copies. It never requests TCC access, opens UI, or captures audio. Native acceptance still requires observing real grants and their preservation across a signed rebuild/relaunch; fixtures do not establish that behavior. This ticket leaves the existing Input Monitoring policy intact for its dedicated implementation.
