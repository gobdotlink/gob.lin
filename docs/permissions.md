# Permissions and recovery

gob.lin requires Microphone for audio capture and Accessibility for global shortcuts and focused-app insertion. When a dictionary term is limited to projects, the same grant lets gob.lin read the frontmost window's document and page address to find the project; see [Dictionary](dictionary.md#project-scopes). Readiness requires only Microphone + Accessibility; onboarding has two required rows and never requests Input Monitoring. The app reads these grants and the informational Input Monitoring status at launch, every second, on activation, and after wake. Launch can open onboarding, but never calls a permission-request API. Allow buttons are the only requests. Microphone status distinguishes not requested, denied, restricted, and allowed; after a decision its button opens Settings. Accessibility shows its current macOS API result, independently of shortcut availability.

Use `scripts/build.sh debug` and `scripts/launch.sh` for signed SwiftPM dogfood. The launcher verifies the exact bundle, rejects unsigned/ad-hoc or hash-bound validation signatures, prints its absolute bundle/executable paths and designated requirement, and refuses to start while another `GoblinApp` is running. It uses an explicit bundle URL and a new instance, avoiding activation of a different worktree. Quit the old process before rebuilding or switching bundles. For Xcode, build the signed Goblin target and pass the product's exact path to `scripts/launch.sh`; `--check` validates either configuration without launching. The local signing certificate is reused, not replaced. Xcode Debug uses a normal executable (`ENABLE_DEBUG_DYLIB=NO`): the generated debug-dylib layout fails hardened-runtime library validation with this local certificate. Hardened runtime and library validation remain enabled; Debug retains its existing debugger entitlement. SwiftUI's debug-dylib-dependent preview support is unavailable in this configuration.

When a toggle appears enabled but the app disagrees:

1. Open Permissions & onboarding and identify **which individual permission** is unavailable. Expand **Running app** and compare its bundle with the entry in System Settings. An old app with the same display name can have a different signing identity.
2. After opening System Settings through gob.lin's **Settings**/**Allow** buttons, return to gob.lin to refresh statuses and retry a failed shortcut even if no status changed. If you opened System Settings independently, choose **Check again** to refresh and retry. The retry calls the normal start path, so its existing permission gates remain enforced; a working tap is not restarted.
3. If the mismatch persists, quit gob.lin and reopen the same signed bundle. Some macOS permission changes require a new process. Recheck the row before changing the grant.
4. Collect local development diagnostics with the API statuses, actual bundle path, signing identifier/designated requirement, and tap-start result. Establish whether Settings registered a different build before manually removing/re-adding any entry. Do not routinely reset TCC or replace certificates.

Apple documents that [mutually compatible designated requirements share access to privacy-protected resources](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements). The same app name or bundle identifier alone does not establish that compatibility. A matching requirement is signing evidence, not proof of a particular hardware or TCC result.

A tap creation failure is reported as **Shortcut unavailable**, preserving the actual permission statuses. An allowed Accessibility API result does not prove that a stale grant caused the tap failure. A run-loop source failure is separately identified as local tap setup failure and recommends reopening/collecting diagnostics. No reset command is offered or executed. Successful tap startup clears the failure. Microphone or Accessibility revocation invokes `onRevocation` before `onChange`, stops services safely, and clears its recovery notice when that permission is granted again. Input Monitoring changes do not revoke or cancel shortcut state. No engine has been selected yet, so dictation acceptance remains dependent on the benchmark and engine integration.

Integration hooks:

- `PermissionModel.onRetry` is owned by `HotkeyService` and calls its idempotent `start()`. Preserve this when the required permission policy changes.
- `PermissionModel.Snapshot.diagnosticFields` exposes separate microphone/Accessibility/Input Monitoring API statuses. `PermissionModel.launchIdentity` provides local-only bundle/executable paths, version/build, PID, signing identifier, code hash, and designated requirement. The hash identifies a build; it is not the stable signing identity.
- Local unified-log events use subsystem `app.goblin.dictation.permissions`, category `recovery`: `launch_identity`, `permission_initial`, `permission_changed` (previous/status), and `tap_start` (`started`, `blocked_by_permissions`, `creationFailed`, or `runLoopSourceFailed`). The persistent development logger can consume the same metadata at `logDiagnostic`; this branch does not add a logging backend. Paths/signing details are not added to copied/shareable diagnostics.
- `HotkeyEventTap` delivers `Result<Void, StartFailure>` to distinguish creation from run-loop setup. Keep cancellation generation checks so obsolete tap results do not update a replacement service.

Run `scripts/check-permissions.sh` for focused synthetic status/retry/revocation probes and `scripts/check-launch.sh` after a signed build for launcher rejection checks on temporary copies. It never requests TCC access, opens UI, or captures audio. Native acceptance still requires observing real grants and their preservation across a signed rebuild/relaunch; fixtures do not establish that behavior. Readiness and diagnostics probes also cover the informational listen-access policy.

## API contract

The shortcut tap uses `CGEvent.tapCreate(tap: .cgSessionEventTap, options: .defaultTap)` for key down/up and modifier flags. It modifies the stream by suppressing its keyed shortcut and Escape during recording. Apple distinguishes this Accessibility-authorized modifying tap from a `.listenOnly` tap, which requires Input Monitoring; see [WWDC19: Advances in macOS Security, synthetic events](https://developer.apple.com/videos/play/wwdc2019/701/). `CGPreflightListenEventAccess()` describes event-listening access, not whether this modifying tap will work. Its result remains visible in diagnostics as “not required” and never gates startup, event handling, recording readiness or insertion.

Shortcut recording uses `NSEvent.addLocalMonitorForEvents` within gob.lin. Apple's same presentation describes local event monitoring as available without background keyboard-monitoring approval. The keyed Secure Input fallback uses Carbon `RegisterEventHotKey`; it does not observe all keyboard input. Focused-app insertion uses Accessibility APIs and synthesized paste events, so Accessibility remains required. Microphone access is still checked before capture. There is no optional listen-only mode to request Input Monitoring for.

Accessibility preflight remains a prerequisite, and actual tap creation remains the runtime check. A failed tap reports a shortcut failure and presents existing recovery guidance; it does not infer missing Input Monitoring. Secure Input still pauses modifier-only shortcuts and rejects protected insertion. Accessibility/microphone revocation still cancels active shortcut state, stops capture through its owner, and presents onboarding. No grant resets or protection bypasses are performed by this change.

Run `scripts/check-permissions.sh` for readiness combinations and diagnostic recovery assertions; these supplied snapshots do not demonstrate system grants or physical keyboard behavior.
