# Audio capture validation

The capture service produces ordered 16 kHz mono Float32 frames and writes them to a private WAV before delivery. The settings level preview and dictation share one microphone input. Explicit warm mode keeps up to 500 ms of pre-roll in memory and keeps the system microphone indicator on. Cold starts remain arming until actual converted samples arrive; speech before the microphone opens cannot be recovered.

## Executed checks

`scripts/check-audio-capture.sh` compiles the capture code with Swift 6 and warnings as errors. It uses the actual platform converter at 16,000, 44,100 and 48,000 Hz with stereo input and a nonzero final tail. It checks contiguous sample positions, readiness before frames, finite samples, mono 16 kHz WAV lengths, and converted sample counts within one rounding sample. The awkward boundaries produced 1,677, 1,628 and 1,626 samples respectively, all nonzero.

The same focused check verifies that recovery skips an active writer, incremental-file recovery of complete samples beyond a stale header while truncating an incomplete trailing sample, explicit cancellation deletion, preservation of 1,600 samples when the input configuration is interrupted, the bounded 8,000-sample pre-roll, no pre-roll leakage into the next session, overload failure, real-clock all-zero/no-callback watchdogs, and invalid storage rejection. These checks address audio loss and storage correctness; they do not simulate hardware acceptance or a long recording.

The app builds with the capture service and the settings preview adapter. No dependency or Xcode project membership changes are needed: Xcode uses the GoblinEngines package product.

## Recovery and cancellation

Completed WAV files have their header and data synchronized and are renamed before stop returns. Active files use `.partial.wav` and checkpoint approximately once per second. Recovery takes a nonblocking exclusive writer lock, skips files that are still recording, repairs the header from complete bytes on disk and truncates an incomplete final sample. Finalization and cancellation retain the lock through the rename or deletion. Process-crash recovery can preserve kernel-written audio; storage or power loss cannot promise bytes not yet synchronized. Cancellation deletes the session's recording intentionally. Device, permission, callback, digital-silence, conversion and storage errors retain recoverable prior audio and require the caller to end that session before starting another.

Callbacks run on one serial processing queue and must return promptly. Actor consumers should yield into one ordered stream and bound their own buffering or fall back to the durable recording. Audio ingress is bounded to two seconds; processing overload fails explicitly rather than dropping samples silently. No content is sent to a network service by capture.

## Capture failure corrections

Failure preservation derives the retained sample count from complete physical WAV payload bytes before checkpointing. A partial write can therefore preserve audio that reached disk even though that buffer never reached the live consumer. The existing first storage failure remains the reported error. A targeted temporary-file probe used a per-process file-size limit, without filling a disk: the write threw after ten complete samples reached an 84-byte file; preservation retained all 84 bytes and reopened with ten samples.

The amplitude watchdog now remembers finite nonzero native input under the existing ingress lock, resetting that flag at begin and resume. Before valid input, an entirely zero stream still fails after five seconds. After valid input, continuous all-zero data may represent a legitimate gated pause and no longer ends capture by amplitude alone. The adapted focused check retained later input across a pause exceeding five seconds, finalized all 11,680 samples, and verified initial-zero detection after both resets. Callback stalls, timestamp gaps, overflow, permission loss, and real device/configuration checks remain in force.

This accepts a deliberate limit: hardware mute or receiver silence after valid input can continue until the user stops or an independent failure is detected. Initial zero-only gated input and silent warm/preview reopen cycles remain unresolved. No new timeout, silence detector, or retry state was introduced, and no physical gated input was tested.

Normal input failure closes the failed engine before synchronously notifying preview observers, so a callback-owned warm replacement survives. Idle sleep uses the opposite order: preview receives the existing systemSleep failure first, then the final close removes any warm input reopened by the callback. Active-recording sleep interruption and the selected-device positive-state guard are unchanged. Source assertions and synchronous ownership replay checked both orders, including active-processor retention; they do not prove physical sleep/wake behavior. Existing sleep wording and diagnostics remain in use.

The native check skips built-in scenarios when no built-in device is identified, rather than labeling system-default capture as built-in evidence. No new hardware run or 30-minute rerun was performed for these corrections. The focused capture checks and app build are the required rechecks; native integration remains independently owned.

## Normal-stop boundary correction

Normal stop records a `mach_absolute_time` cutoff inside the existing `stop(sessionID:)` call. Ingress remains open until ordered input covers that cutoff. The whole straddling buffer is queued before acknowledgment, then ingress closes and conversion/file finalization drain. This retains a bounded tail of up to one input buffer after the cutoff. No public API or caller changes are needed.

Coverage requires valid host and sample timestamps at the native rate, contiguous sample positions, increasing host times, and adjacent host ranges within one native sample of rounding. Host-range arithmetic is checked for overflow and future capture times. The acknowledgment deadline is 1.2 times the last observed buffer duration, capped at 120 ms. Invalid mapping or an unacknowledged deadline uses the existing `noCallbacks` failure and retains accepted audio; it does not return a successful whole-recording result. File processing and synchronization follow acknowledgment, so the deadline is not a guarantee for total stop latency. Explicit cancel and failure close ingress immediately and resolve a pending stop once.

The focused check now exercises a delayed straddling buffer with an exact last-sample assertion, rejection of subsequent input, already-covered cutoffs, a cancelled deadline across resume, bounded timeout with retained audio, invalid/absent/future/overflowing/reordered timestamps, and cancellation before registration or during a pending stop. It also checks that interruption retains the original failure. The existing converter, storage, watchdog and cancellation checks still pass.

A short signed native comparison used six varied capture lengths and the current system-default input; the selected external device was unavailable. The baseline at `ff68c356e10f94229c1451e44f0ed06ef068c735` silently omitted 52.05–96.93 ms of input preceding the probe's stop-call timestamp in all six runs. The correction covered the cutoff measured inside the service in all six runs, with nonzero audio and no failures. Observed buffers were 100 ms, capture-to-callback lag was 101.00–110.63 ms, and maximum adjacent host-range discrepancy was 0.375 microseconds. Final-candidate stop took 19.16–96.87 ms; retained post-cutoff tails were 7.48–89.11 ms. An earlier six-run observation before the explicit late-acknowledgment deadline guard measured 11.64–109.45 ms. Every finalized WAV was reopened and its exact length, finite samples and nonzero peak checked. A separate native cancellation during pending stop took 2.27 ms, made stop throw cancellation, and left neither a finalized nor a partial recording. Both own probes closed their engines and exited. Aggregate results are in `audio-capture-stop-results.json`.

These observations establish the buffered-input loss mechanism for this probe. They do not explain prior recognition-ending mismatches or prove physical word preservation. Full hotkey-release-to-text latency remains unverified: the existing 40 ms release hold-back plus the slowest measured capture stop leaves almost no room under the 150 ms target. No target was relaxed. Other hardware clock mappings, external-device delivery timing, actual sleep/unplug, and a new 30-minute run were not tested in this correction. The earlier 30-minute evidence applies to its stated revision.

Successful preview input now clears only the exact stale unavailable-selection fallback warning. Other errors remain visible. The app build checks this adapter; physical device reconnection was not exercised.

## Pinned device input

Capture used to open the engine input node, which binds the system default input before the selected device can be set. With AirPods connected as the default input and the DJI selected, the system log showed the same sequence in two app hangs. The node opened a default-device aggregate of the AirPods input and output, and the AirPods switched to their 24 kHz call profile. gob.lin then selected the DJI while the engine's own thread reselected the rebuilt aggregate. The engine logged a device error, and the main thread made no further progress until the app was force-quit, 13 s and 32 s later.

Capture now opens a HAL input unit, enables input, disables output and sets the resolved device before initializing it. The system default is never opened unless it is the resolved device. The unit delivers the device's own rate and channels as non-interleaved Float32 in chunks of at most 100 ms. These match the previous tap buffers, so the stop deadline and the live-frame backlog keep their measured margins. A sample-time gap after the first delivered chunk ends that chunk and still fails the recording. Bluetooth input skips about 100 ms once, at the second or third callback, before anything has been delivered; that partial chunk is discarded. Device listeners for liveness, nominal rate and input stream configuration replace the engine configuration notification. They keep the existing guard: only a stopped unit, a changed or dead device, or a changed rate or channel count interrupts capture.

Timestamp probe on this Mac, 3 s per device: built-in and DJI input stayed contiguous at 512 frames, with host-time error at most 0.29 µs and 2.38 µs against a 20.8 µs sample period. AirPods input at 24 kHz jumped by 2,258–2,475 frames once, at callback 2 or 3, then stayed contiguous.

Native capture probe after the change, with AirPods as the default input and output: the selected DJI passed cold and restart, and warm capture kept 8,000 pre-roll samples. Missing-UID fallback to the AirPods passed with 46,400 nonzero samples. Cancellation removed its partial file. Throughout the DJI scenarios, the AirPods output stayed at 48 kHz and their input was never running. Built-in input delivered digital silence with the lid closed, as before.

Real app: with AirPods connected and the DJI selected, three dictations started with first audio after 178–217 ms, opened only the DJI, and left the AirPods at 48 kHz. A preview and a dictation with the AirPods input selected also completed; the first dictation's audio arrived after 475 ms. No default-device aggregate was created.

Still untested: physical unplug during capture, an actual sample-rate change, sleep and wake with this input path, and built-in speech with the lid open. Opening the device runs on the capture actor's dedicated executor; with a Bluetooth input selected, audio starts about 0.2–0.5 s after the device opens.

## Muted and silent input warnings

The opened device's reported mute or zero input volume now produces a nonterminal warning once fresh audio callbacks are flowing. Nonzero noise cannot suppress this device evidence. Without a device-reported cause, exact-zero samples warn after five seconds initially, or fifteen seconds after nonzero input. No RMS cutoff is applied. Flowing digital silence no longer triggers the former five-second terminal failure; missing callbacks and other capture failures retain their existing handling. This supersedes the initial-zero timeout described in earlier results above.

A certificate-signed probe exercised the actual capture service on the C920 webcam and built-in microphone. Both reported zero volume within the existing 250 ms polling interval, continued capturing for more than six seconds, and propagated warning changes to the session and preview. The webcam still delivered nonzero samples while its volume was zero. Explicit mute, restoring volume, and unmuting were exercised during each recording. All original mute and volume values were restored.

The built-in microphone delivered exact zeros throughout this setup. Restoring its volume therefore changed the specific warning to the generic silence notice. A retained preview warned after about 5.2 seconds of digital silence; starting a new recording immediately cleared that published notice. The processor checks also cover the five/fifteen-second boundaries, callback freshness, quiet nonzero input, warning-only zero streams, and reset behavior.

The signed release app's Audio preview visibly showed the zero-volume notice while the webcam meter still read 5%. Restoring volume cleared the notice and returned the meter to 22%. Switching the running preview to another device showed a pending Stop control, which successfully stopped the pending preview. The previous device selection and volume were restored. Package smoke checks, all 34 Swift tests, media ownership checks, and the universal Xcode Release build passed.

Unsupported devices that emit nonzero hiss remain outside the conservative sample-only detector. No noise-floor calibration, physical headset mute, or Bluetooth startup acceptance was performed in this correction.
